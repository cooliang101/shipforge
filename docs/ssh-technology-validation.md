# SSH Technology Validation

## Decision

ShipForge uses `russh` and `russh-sftp` for the built-in `linux-ssh` Driver. It enables the `ring` crypto backend and compression support; the default AWS-LC backend was rejected after requiring an external NASM installation on the Windows GNU toolchain. The optional RSA implementation is disabled because its dependency has an unresolved timing-side-channel advisory, so the MVP accepts modern non-RSA SSH identities only. The selected configuration exposes Tokio-native connection, command-channel, SSH Agent signing, and SFTP APIs.

## Verified in Code

- Host Keys are never accepted implicitly. Capture mode records a fingerprint while rejecting the first connection; strict mode accepts only the fingerprint confirmed through the TUI.
- Fingerprint capture and authenticated connections share a client configuration with TCP `nodelay` enabled. TCP, handshake/Host Key, credential and authentication phases consume one absolute deadline and report only fixed phase names. This avoids cumulative small-packet delays in sequential command exchanges while making a timeout attributable without exposing raw SSH or key errors. The Linux loopback regression retains its original 180-second deadline; RET-01's controlled client-only comparison completed the full case in 4.16 seconds after the baseline timed out.
- The supported `IdentityFile` input is a local regular file of at most 1 MiB. The final file cannot be a link/reparse or special file, and obvious Windows UNC/device paths are rejected. Blocking metadata/read/decode work is isolated behind a process-wide single-flight OS thread; a permanently stalled read cannot multiply workers or hold Tokio shutdown, but that one thread is not forcibly killable and may block further file-key attempts until process exit. Mapped drives, network mounts and parent-directory junctions are outside support because this layer cannot reliably identify all of them.
- Remote command timeout/cancellation first settles an already-known exit status, then attempts TERM, KILL and channel closure inside a separate bounded cleanup window. Failure to confirm remote termination remains an interruption, never an invented success.
- Unix Agent sockets, Windows OpenSSH named pipes, and Pageant have explicit discovery paths. Agent identities expose only fingerprint, comment, and certificate status to selection UI.
- Agent discovery observes a cancellation token and does not contact a deployment Destination.
- SSH config discovery reads only concrete direct `Host` blocks and treats the result as editable TUI candidates. `Include`, `Match`, wildcards, and `ProxyJump` are intentionally outside the MVP.
- `linux-ssh` target validation rejects non-normalized roots, unsafe systemd unit names, credential-bearing or ambiguous health URLs, unsupported health schemes, and unknown fields.
- The in-process SSH/SFTP protocol test covers authenticated command execution, bounded streaming upload progress, a partial-write failure followed by cleanup and retry, no-clobber conflicts, cancellation cleanup, remote SHA-256 success and mismatch, Release Prepare, Component-level atomic `current` activation, final observation, and Destination-side HTTP health execution over one real SSH session.
- The opt-in two-container acceptance suite uses real Debian/OpenSSH endpoints and the production deployment service for single/joint deployment, explicit rollback, destination-side HTTP failure compensation, and cancellation. See [live evidence and limits](validation/linux-ssh-acceptance.md); this does not establish systemd or cross-platform acceptance.
- A separate [WSL systemd acceptance suite](validation/systemd-acceptance.md) now verifies a no-port Worker, stability failures, compensation, and historical/undeployed rollback. Its temporary root control connection does not establish non-root service authorization or the complete platform matrix.

## Release-Gate Live Checks

Disposable OpenSSH environments must verify successful SSH Agent and IdentityFile authentication with distinct keys, SFTP upload/cancellation, command cancellation, Host Key rotation rejection, and behavior from Windows, macOS, and Linux clients. Exact release-binary PTY/ConPTY smokes verify `q`, idle Ctrl+C bytes followed by `q`, exit status and platform-observable cleanup. Unix also compares PTY termios and requires ordered alternate-screen/cursor sequences; Windows ConPTY checks ordered cursor recovery and requires paired alternate-screen transitions only when ConPTY exposes them. These checks belong to the `QA-01` release gate and do not run in the default test suite. No production Environment may be used.

The QA-01 candidate adds a pinned native matrix for Windows GNU, Linux GNU and macOS arm64 on both stable Rust and the declared Rust 1.88 minimum. Stable Linux/macOS jobs run their native external OpenSSH gate; stable Windows runs its runner-safety suite, while the Windows external gate is a separate explicit run that requires an already-running system Agent. Stable jobs also run the performance gate, and both toolchains build and smoke the exact release binary. CI installs toolchains only inside ephemeral runners—it does not require changing a developer's local Rust installation. Current local evidence and remaining native-CI requirements are recorded in [QA-01 validation](validation/qa-01.md); platform support is not claimed until those jobs pass.
