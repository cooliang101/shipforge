# SSH Technology Validation

## Decision

ShipForge uses `russh` and `russh-sftp` for the built-in `linux-ssh` Driver. It enables the `ring` crypto backend and compression support; the default AWS-LC backend was rejected after requiring an external NASM installation on the Windows GNU toolchain. The optional RSA implementation is disabled because its dependency has an unresolved timing-side-channel advisory, so the MVP accepts modern non-RSA SSH identities only. The selected configuration exposes Tokio-native connection, command-channel, SSH Agent signing, and SFTP APIs.

## Verified in Code

- Standard SSH password authentication is supported on the Windows client. Both connection forms expose masked `F5` entry; user-scoped DPAPI ciphertext survives registry reload. The password protocol regression verifies a rejected host key receives no password, wrong-password rejection, cancellation, timeout, exec, SFTP, Release prepare/activation and saved-credential reuse. Existing private-key and SSH Agent paths remain enabled. This does not imply keyboard-interactive/MFA support or successful deployment to an arbitrary server.

- Host Keys are never accepted implicitly. Capture mode records a fingerprint while rejecting the first connection; strict mode accepts only the fingerprint confirmed through the TUI.
- Fingerprint capture and authenticated connections share a client configuration with TCP `nodelay` enabled. TCP, handshake/Host Key, credential and authentication phases consume one absolute deadline and report only fixed phase names. This avoids cumulative small-packet delays in sequential command exchanges while making a timeout attributable without exposing raw SSH or key errors. The Linux loopback regression retains its original 180-second deadline; RET-01's controlled client-only comparison completed the full case in 4.16 seconds after the baseline timed out.
- The supported `IdentityFile` input is a local regular file of at most 1 MiB. The final file cannot be a link/reparse or special file, and obvious Windows UNC/device paths are rejected. Blocking metadata/read/decode work is isolated behind a process-wide single-flight OS thread; a permanently stalled read cannot multiply workers or hold Tokio shutdown, but that one thread is not forcibly killable and may block further file-key attempts until process exit. Mapped drives, network mounts and parent-directory junctions are outside support because this layer cannot reliably identify all of them.
- Remote command timeout/cancellation first settles an already-known exit status, then attempts TERM, KILL and channel closure inside a separate bounded cleanup window. Failure to confirm remote termination remains an interruption, never an invented success.
- Unix Agent sockets, Windows OpenSSH named pipes, and Pageant have explicit discovery paths. Agent identities expose only fingerprint, comment, and certificate status to selection UI.
- Agent discovery observes a cancellation token and does not contact a deployment Destination.
- SSH config discovery reads only concrete direct `Host` blocks and treats the result as editable TUI candidates. `Include`, `Match`, wildcards, and `ProxyJump` are intentionally outside the MVP.
- `linux-ssh` target validation rejects non-normalized roots, unsafe systemd unit names, credential-bearing or ambiguous health URLs, unsupported health schemes, and unknown fields.
- The current in-process SSH/SFTP protocol test covers pinned authentication, bounded transfer progress, partial-write cleanup/retry, exclusive upload, cancellation, SHA-256 verification and the production in-place Driver. It executes the embedded Python publisher in temporary directories and simulates service success, known failure and missing exit status. It does not run real systemd/PM2 services; application replacement is per-file, not an atomic directory switch.
- Service actions use structured argv and the configured original application root as their quoted working directory. systemd supplies a preset; custom services have no implicit systemd dependency. Unknown command outcomes block competing recovery commands.
- The two-container [Linux acceptance](validation/linux-ssh-acceptance.md), [WSL systemd acceptance](validation/systemd-acceptance.md) and [SVC-01 Node/PM2 results](validation/svc-01.md) describe the retired version-directory engine. Their full deployment fixtures are no longer current acceptance entry points. Current actual deployment evidence is in [in-place validation](validation/inplace-deployment.md); publisher fault coverage is in [WSL validation](validation/wsl-inplace-faults.md).

## Historical release-gate checks

QA-01 validates the Windows x64 GNU client locally against disposable Linux OpenSSH servers: distinct IdentityFile/Windows OpenSSH Agent keys, SFTP upload/cancellation, command cancellation, and strict Host Key rotation rejection. Exact release-binary ConPTY smokes verify `q`, idle Ctrl+C bytes followed by `q`, exit status, and ordered cursor recovery; alternate-screen transitions must be paired only when ConPTY exposes them. The live and terminal gates require explicit invocation and never use a production Environment.

The MVP supports only Windows x64 GNU, tested with the existing Rust 1.96.1/MinGW toolchain. Current local checks and disposable-fixture entry points are in [tests/README.md](../tests/README.md); the personal-use delivery scope is in the [roadmap](roadmap.md). GitHub test workflows are removed; pushing only synchronizes repository content. Linux/macOS runners remain unsupported experiments, not release gates. Rust 1.88 remains declared metadata, not independently verified minimum-version compatibility. [QA-01](validation/qa-01.md) preserves its original evidence and support limits.
