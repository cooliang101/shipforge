# 部署助手职责

2026-09-07 用户明确修正产品定位。本文取代旧文档中强制版本目录、current 软链接、空目录接管和多版本管理的要求。

ShipForge 兼容应用现有的发布方式，不改造应用的运行方式。流程只有：构建产物、上传校验、把上一版应用保存为一个压缩包、发布到既有目录、执行用户配置的启停命令、验证；确认发布失败时用上一版应用压缩包恢复并执行恢复命令。

2026-09-08 明确按个人使用定位：用户管理自己的项目和服务器，信任所配置的脚本。助手不承担企业权限、审批、合规审计或流水线治理；安全工作以防误操作、防泄密和可理解的失败处理为限。保留现有校验，不以“个人使用”为由关闭保护，也不为穷尽极端场景增加配置与操作负担。

- 不要求迁移目录、使用 releases/current、修改 systemd/Nginx 配置或改变应用工作目录。
- 不新增权限、不改 sudoers；需要 sudo 时使用账号已有权限。
- 不备份、迁移、恢复数据库、附件、日志或其他运行数据。应用包之外的已有文件保持原样。
- 上一版压缩包仅用于本次应用发布失败回退，不扩展为备份管理或多版本保留系统。
- 发布范围以构建产物为准，不能打包整个混有运行数据的目录，也不能递归删除整个部署目录。首次接入时明确上一版应用文件范围。
- 保留必要的传输校验、路径校验、操作记录和结果判断。服务命令结果未知时先查明结果，不能重复启停或盲目覆盖。
- 不声称覆盖文件具有原子切换性质，不替应用处理数据一致性。

## 当前实现

内置 linux-ssh 驱动统一采用原目录发布，没有模式开关。移除了旧驱动的 current 切换、版本目录、远端审计标记、多版本保留和目录接管流程。

每个组件的 `root/.shipforge-deploy` 仅存操作状态、一个上一版应用压缩包及发布期间的临时上传包。先验证产物及发布范围、压缩原应用，再停止服务、逐文件替换、执行启动/更新命令和检查；明确失败时恢复上一版文件并执行恢复命令。上传尚未应用时可按本次操作身份丢弃；已应用或结果未知时不清理现场。

首次应用范围是产物的顶层文件/目录，后续合并已记录范围以移除旧静态资源；范围之外不读取内容、不备份、不覆盖。产物必须仅包含应用文件。服务命令及只读命令检查在原 root 执行，沿用现有程序配置。远端需已有 Python 3，工具不安装依赖。

SSH/SFTP 传输、已知失败恢复及未知结果阻断使用回环服务器和临时目录验证。路径/链接、内容漂移、压缩包损坏、取消与操作身份使用隔离测试验证。不能将这些测试解释为抵御服务器上同权限恶意并发修改，也不承诺整个目录原子发布。
