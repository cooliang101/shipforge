# 个人使用指南

ShipForge 在 Windows x64 上运行，把本机构建出的应用文件发布到已有 Linux 目录。服务器需已有 SSH/SFTP、Python 3 及项目使用的服务工具；本机需具备项目自己的构建环境。

## 运行与配置复用

在交互式 Windows 终端中运行，建议窗口至少 100×28：

```powershell
& D:\cdoe\shipforge\target\release\shipforge.exe
```

1. `F6` 选择中文，`F1` 查看当前页帮助。项目列表选择已有项目；没有登记时按 `o` 浏览到项目目录，按 `s` 选择。
2. 有效的 `shipforge.yaml` 会直接打开概览，复用已保存的组件、环境、连接和服务。按 `e` 修改配置，逐层 Apply，再以 `p` 预览、`c` 保存；不要手工改 YAML 或 `_shipforge`。
3. 保存后按 `Esc` 返回项目列表，重新打开同一项目，核对环境、组件、连接端点、root、构建与服务命令。重新启动后也沿用项目文件和用户级连接。
4. 按 `d` 选择实际要发布的组件，检查计划中的服务器、目录和应用范围，再确认执行。保存配置不会部署；构建产物只能包含应用文件。运行数据不能混在产物对应的应用子目录里。
5. 完成后查看每个组件的结果；按 `l` 看日志。服务没有配置健康检查时，成功不代表做过业务接口验证。

## 更新程序

先在所有打开的 ShipForge 中正常退出：空闲页按 `q`；有任务时按提示取消并等待结束。运行中的 exe 无法被 Windows 覆盖，若构建提示“拒绝访问”，先检查是否仍有程序打开，不强制结束正在部署的进程。

在仓库取得所需版本源码后，复用已有 Rust/MinGW 构建：

```powershell
cargo build --release
& .\target\release\shipforge.exe
```

构建失败时不要把仍存在的旧 exe 当成更新成功。不使用 `--target`，也不更换输出目录。只需要释放开发缓存时用 `cargo clean --profile dev`，它保留 release exe。

更新不需要重新建项目或连接。保留项目根的 `shipforge.yaml` 和当前 Windows 用户的 `%APPDATA%\ShipForge`（连接、加密凭据、历史与日志等）；需要本地备份时先退出程序，副本按私有资料保存。密码密文绑定 Windows 用户，换用户或机器后应从连接管理重新输入，不能靠复制密文迁移登录能力。旧程序未必兼容新配置/历史，降级不能只替换 exe 后盲目继续部署。

## 失败处理

| 提示或现象 | 下一步 |
| --- | --- |
| 构建失败、产物不存在或为空 | 查看失败步骤的程序、参数、工作目录和 artifact；修正本机构建或 TUI 配置后重新预检。 |
| SSH 连接、Host Key 或密码验证失败 | 项目列表按 `c` 管理连接；核对主机和端口，通过可信渠道确认指纹。密码变化用 `F5` 重新输入，不跳过 Host Key。 |
| 上传校验、空间、权限或应用文件漂移错误 | 先看具体失败阶段；确认上传包、目标空间和应用范围。保留现场，不删除部署根目录或通过重置元数据绕过检查。 |
| 明确失败，上一版已恢复 | 分别核对主失败、恢复结果和服务检查；修复原因后重新预检。失败部署不会因为恢复成功就变成成功。 |
| 结果未知、恢复失败或远端状态文件损坏 | 保存 Deployment ID，从历史与日志查看最后已知阶段，在服务器只读核对进程、文件和状态。未查明前不重复发布/启停，不删除 `.shipforge-deploy` 或手工把状态改成 stable。需人工处理时按实际证据恢复应用；工具不替你恢复数据库。 |
| 执行成功但历史/日志保存告警 | 以已知执行结果与告警分别处理；先查看当前结果、日志和本机存储问题，不把记录失败当作远端没有执行。 |

历史详情按 `l` 查看日志，可按 `e`/`s` 预览并导出日志/摘要。回滚仅在历史证据和远端唯一上一版均可用时进行；历史列表不是多版本备份库。

正常退出会恢复终端；活动任务的 `Ctrl+C` 先请求取消。强制结束、断电或关闭宿主可能留下未知结果，下次启动先看待核实记录。逐文件发布不保证整个目录原子切换。

详细按键见 [TUI 指南](tui-guide.md)，配置规则见[配置指南](configuration-guide.md)，交付与验证范围见[路线图](roadmap.md)。
